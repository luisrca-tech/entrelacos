### Transaction and dispatch rules

1. `readExisting` selects the exact site/request and original account/environment from stored rows. Missing, ambiguous or foreign association does not create anything. Nonterminal parsing reuses the current snapshot/consent semantics; completed validation is private to this new repository and does not relax A's replay reader.
2. `armExisting` uses the reservation's same request advisory key, site/authority lock order and original account row lock before intent/operation/committed-association inspection. First-dispatch admission requires REQUESTED intent, REQUESTED operation, attempts0, no lease/provider/receipt/resolution, exact HELD amount and unchanged COMMITTED consent. Fresh locked authority must match that original account/destination; AWAITING_AUTHORIZATION is not auto-approved. Any prerequisite denial makes no provider call and retains the original rows/hold.
3. In that transaction, CAS changes only the existing intent/operation to PROCESSING, operation attempts to1 and the once-generated lease fence; preserve immutable snapshots, request/hash, amounts, association and held amount. Return ARMED only after positive commit acknowledgment. A lost acknowledgment returns uncertainty with no dispatch by that caller. Reading already armed rows returns EXISTING, never another dispatch grant.
4. Only the ARMED caller invokes the captured dispatch callable once, after rechecking its captured proof's time validity. Lease expiry never grants takeover/retry. A crash before invocation may strand a hold despite no actual transfer; conservative existing-only reconciliation is selected over unsafe redispatch. No Promise.race, timer-based completion, automatic retry or provider cancellation is introduced. Genuine in-flight port promises retain ownership until actual settlement; permanently pending work remains pending. Later native dispatch/approval race guarantees require separate A/provider implementation and acceptance.
5. `recordObservation` reacquires the same original locks and exact retained fence. It may fill a null provider reference once in both original rows, or confirm the exact existing reference; it cannot repoint to another transfer. Accepted nonterminal results remain PROCESSING/HELD. Uncertain/rejected results become UNKNOWN/HELD with sanitized local reason, preserving attempts1 and the original fence. It cannot overwrite a terminal effect committed concurrently. An old result with a changed fence or contradictory provider reference is rejected; no hold is released.
6. `reconcileExisting` never calls dispatch. It uses lookup and, only when supplied a completion proof reference, `postCompleted`. Observation absence/error/rejection retains uncertainty and the original hold. No mutable current replacement account/readiness is required to recognize an already completed original transfer; settlement recognizes historical proof without granting a new action.
7. `postCompleted` locks the original account/intent/operation/association, reads the retained fence and immutable durable proof in that transaction and validates them. No new provider call occurs inside the transaction. Exact historical fence identity is required; expired time is not authority for another dispatch and does not erase authentic later completion of the original attempt. Before the first terminal write, record a single DEBIT for original total amount, linked to original withdrawal/operation, kind `WITHDRAWAL_COMPLETED`, BRL, with null payment/event/compensation references. The private effect key is `withdrawal.completed.v1:` plus SHA-256 of canonical `[siteId,accountId,environment,withdrawalId,operationId]`; uniqueness is independent of a possibly inconsistent provider reference.
8. In the same transaction, CAS the held original intent to COMPLETED/CONSUMED/reserved0, pin provider/bank receipt/resolution time, and the original operation to SUCCEEDED. Preserve the original lease fence, attempt1, request snapshot and COMMITTED consent. A debit is recorded before the commitment is consumed. An exact already committed proof/effect returns DUPLICATE; inconsistent existing entries or terminal rows fail closed. Any partial insert/CAS/query failure rolls back the whole unit. Lost terminal commit acknowledgment is unresolved until the exact original rows/proof/effect are reread; retry cannot insert another debit.

The repository does not INSERT into withdrawal intent/request/operation, receiving or inbox tables; it never writes proof custody, regenerates consent, releases a failed/cancelled hold, refunds, compensates or edits a ledger entry. Existing schema uniqueness and fixed single-attempt admission make disjoint concurrent calls safe locally, subject to separately authorized physical transaction tests.
